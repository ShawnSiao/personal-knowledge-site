# 案例与进阶：什么时候才值得增加复杂度

读业界案例的价值，在于理解团队面对的问题和约束，而不是照搬架构图。一个拥有大量跨系统资料的平台，与只有几十页手册的个人项目，可能需要完全不同的设计。

本章区分三类内容：来源明确的案例事实、本站的设计推断，以及尚未在本站运行的进阶方案。

## 1. Slack：先维护既有的可见范围

Slack 的公开案例强调 AI 能看到的内容与请求者原有可见范围一致，详见[[learning/ai/rag-guide/01-problem|第一章]]的原始来源。这个案例适合用来理解权限如何参与检索，不适合用来推导「所有 RAG 都天然安全」。

本站的设计推断是：企业已有成熟搜索和身份系统时，应优先考虑复用，减少出现两套权限语义的机会。代价是可能需要适配旧系统的检索能力与延迟，不能只比较模型回答速度。

对纸舟项目，验收方式是同一问题在 staff 与 security 两个身份下得到不同的证据集合，而不是让模型口头保证保密。

## 2. Dropbox：相关性标注本身就是工程工作

Dropbox 的标注流程已在[[learning/ai/rag-guide/07-evaluation|评估章节]]给出来源。值得关注的是先用人工判断校准自动评估，再扩大标注，而不是把模型评分当作真值。

本站的设计推断是：资料中的缩写、团队术语和时间上下文，经常决定某个结果是否有用。若评委不知道这些背景，大量自动标签也可能只是大量一致的错误。

纸舟可以从十几题开始，让两位评阅者独立标注，讨论分歧，再写成规则。此时不需要先搭建复杂标注平台。先解决判断标准，再解决规模问题。

## 3. Anthropic：先看指标，再看百分比

上下文补充和重排序的实验数字在[[learning/ai/rag-guide/03-chunking|第三章]]中列出。适合借鉴的是实验拆分：分别观察加入上下文、关键词通道和重排序后的变化。对一个新语料集，仍需要复现自己的对照实验。

本站的推断是：如果大量失败来自片段缺少标题背景，先补标题路径可能值得尝试；如果失败来自旧文档优先命中，补充上下文并不能替代版本过滤。技术名称相同，不代表错误原因相同。

## 4. GraphRAG 适合哪类问题

「数据库备份保留几天」是局部事实查询；「这半年所有事故中反复出现了哪些组织协作问题」需要跨资料汇总。后一个问题可能难以由少量相似片段完整覆盖。

微软研究的 GraphRAG 工作讨论面向整体语料的查询式摘要，通过图结构与社区摘要支持由局部到全局的回答。[GraphRAG 论文](https://arxiv.org/abs/2404.16130) 这不是证明任何事实查询都需要知识图谱。

图提取会新增实体消歧、关系错误、摘要失真和更新成本。例如两个系统都叫「Atlas」，错误合并后会污染多条关系。若项目主要查询明确条款，应先让普通检索工作稳定；只有全局问题占比和失败样例支持，才增加图结构实验。

## 5. Agentic RAG 何时值得尝试

复杂问题可能需要拆成子问题、执行多次检索、比较结果，再决定是否继续。相比单次检索，这给系统更多机会，也增加了调用次数、延迟与不确定性。

可以给检索代理限定只读工具、最多轮次、总预算和停止条件。每次新增检索都应回答一个明确缺口，而不是因为模型还想继续就无限搜索。保留原始问题与每次改写，方便发现意图漂移。

本站建议先比较两种简单基线：单次查询，以及事先定义的两次查询。只有动态规划明显解决了基线无法处理的问题，才有理由承担代理运行控制的成本。这里是实验建议，不是已验证的收益结论。

## 6. 长上下文何时能替代检索

当资料很少且权限一致时，将完整资料放入上下文可以减少检索漏失。但它仍受 token、成本、位置效应和更新机制影响。全量上下文还可能把不必要的敏感资料一并交给模型。

因此比较应在同一问题集、同一资料快照和同一身份条件下进行。记录成本、延迟、正确性与可追溯性，而不是只比较某一道题的表现。

## 7. 一张选择表

| 观察到的主要失败     | 优先实验                 |
| -------------------- | ------------------------ |
| 标识符或错误码错配   | 精确字段与关键词处理     |
| 同义表达找不到       | 查询扩展或语义检索       |
| 片段缺少背景         | 标题路径与父段落补充     |
| 候选有答案但排名靠后 | 重排序                   |
| 同主题旧版本混入     | 版本与生效规则           |
| 需要跨全文归纳       | 全局摘要或 GraphRAG 对照 |
| 需要多次查证才能回答 | 有预算的多步检索         |

这张表是排查起点，不是自动选型器。同一个故障可能有多个原因，应该先检查真实输入和中间结果。

## 本章练习与判断依据

从现有系统挑三条失败，分别写出证据、根因假设、最小实验和停止条件。每次只增加一个机制。

如果无法说清新机制要修复哪种错误，就暂缓加入。可以公开记录「暂无可靠数据」，比把论文或厂商案例的数字搬成自己的项目成果更有价值。
