# 部署与运维：让更新、权限和失败都有确定行为

本地问答脚本只有一个调用者和几份文档，很多问题不会出现。真实服务可能同时面对文档更新、权限撤销、索引故障、模型超时和重复请求。部署不是把脚本放到服务器上运行，而是为这些变化定义可验证的行为。

本章提供原创部署设计，不包含已经在真实客户环境验证过的性能承诺。

## 1. 把离线入库与在线问答分开

离线部分负责读取资料、解析、分块、建立索引和质量检查。在线部分负责身份确认、检索、证据组装、生成与输出检查。两者通过一个已验证的索引版本连接。

这样文档解析失败时，不会把半份新资料直接暴露给查询。在线服务也不应在每次问题到来时重新下载全部文件或生成全部向量。

一个最小部署可以包含问答服务、索引服务和作业进程，但不必一开始拆成大量微服务。首先保证每个阶段的输入输出和故障责任清楚。

## 2. 索引发布采用可切换版本

为新资料构建索引 B，旧索引 A 继续处理查询。完成文档数量核对、权限抽检和固定问题回归后，将逻辑别名切到 B。保留 A 一段受控时间，便于退回。

切换不只涉及向量，还应包括元数据、分块文本和配置。若向量来自 B，引用定位却读取 A，就可能出现「检索到了，但来源显示另一段话」。

回滚也不是简单恢复旧目录。旧索引可能包含已经撤销访问的资料；恢复服务时仍要套用当前权限和删除要求。可回滚性不能凌驾于数据治理。

## 3. 权限检查不能只放在页面上

服务端从认证会话取得租户和群组，再限制候选范围。返回给前端的片段、预览和引用同样需要校验。不要允许前端提交任意 group 字段来模拟身份。

Azure 的安全过滤文档说明了一种按安全标识过滤搜索结果的模式，但过滤表达式本身不是身份认证系统。谁有权代表哪个群组，仍由应用层确认。[官方安全过滤说明](https://learn.microsoft.com/en-us/azure/search/search-security-trimming-for-azure-search)

测试时要覆盖同一个问题由不同身份提问、成员被移出群组、文档变为私有，以及旧缓存是否继续暴露内容。

## 4. 缓存键包含的不应只有问题

如果只按问题缓存回答，管理员问过的问题可能被普通用户命中。至少要把权限范围、语料版本和生成配置纳入设计；权限变化后要能使相关缓存失效。

缓存也可能保存已经删除的事实。一个实用做法是让缓存记录引用的文档 ID 与版本，更新或删除事件触发失效。具体实现依赖系统规模，但验证用例必须存在。

不要把用户身份原文、密钥或全文材料写入普通诊断日志。记录请求 ID、阶段耗时、索引版本、片段 ID、状态与错误类型，通常更便于排障，也减少不必要的数据复制。

## 5. 超时与降级应反映真实结果

给请求设置总 deadline，再为检索、重排序与生成分配阶段预算。重排序超时可以退回初次排名；生成超时可以返回可用证据列表。但界面和日志应说明这是降级结果，不能装作完整答案。

重试只适合可重复且风险可控的操作。查询通常可重试；若系统扩展到创建工单，就需要幂等键和明确的写入状态。用户取消后，服务应停止启动新的下游调用，并根据提供方能力处理已经发出的请求。

## 6. 上线前验证什么

将验收拆成四组，避免「构建成功」掩盖业务问题。

第一组是内容：文档数、拒绝入库原因、来源定位和当前版本。第二组是质量：固定问题集、无答案行为、冲突说明。第三组是边界：权限撤销、缓存隔离、引用伪造。第四组是运行：超时、取消、服务不可用、索引切换和恢复。

发布顺序可以是内部只读试用、少量受控用户、扩大范围。每一步观察失败类型和用户实际任务完成情况；不能用网页打开次数代替问题解决率。

## 7. 成本怎么记录才有意义

以单次请求为单位，分别记录检索资源、重排序调用、生成输入输出与缓存命中。还应记录离线解析和索引更新成本。只计算生成 token，会低估整个系统的维护费用。

模型价格和硬件成本会变化，本教程不填一个无法复用的「每次问答固定价格」。做预算时使用实际账单和可复现负载，注明日期、输入长度、并发、模型配置和统计区间。

## 本章练习与判断依据

在隔离环境模拟三个事件：发布坏索引、撤销某人的权限、生成服务超时。逐项记录期望行为与实际行为。

合格系统应保持旧服务可用、阻止撤权后的访问，并把超时显示为失败或降级。若只能在理想条件下回答问题，还不能称为完成部署验收。
