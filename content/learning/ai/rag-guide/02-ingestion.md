# 文档入库：先保住来源、结构和版本

RAG 的第一份输入不应该是「一长串清洗后的文字」，而应是一组能够追溯到原始材料的记录。如果解析时丢掉了表头、把双栏排版左右交叉拼接，后面的检索再准确，也只是准确地找到了损坏的信息。

纸舟案例里，备份规范有两个版本。入库服务的任务不仅是读取文件，还要保存两者的关系，并说明哪一个可以参与当前回答。

## 1. 最小文档结构

```json
{
  "document_id": "backup-policy",
  "version": 2,
  "title": "备份保留规范",
  "status": "active",
  "effective_from": "2026-08-01",
  "source_uri": "https://example.org/handbook/backup",
  "allowed_groups": ["staff"],
  "parser_version": "markdown-v1",
  "content_hash": "由实际内容计算",
  "text": "生产数据库备份保留 30 天。"
}
```

这是一份虚构教学记录，网址不是实际资料入口。document_id 表示逻辑文档，version 表示一次不可变修订；文件名改动不应自动变成一份新制度。content_hash 用于发现字节内容变化，不能替代业务版本。两个相同正文的文件也可能具有不同权限和生效范围，不能仅凭哈希把它们的访问权限合并。

effective_from 应来自文档管理规则，而不是操作系统最后修改时间。复制文件会改变时间戳，未生效草案也可能比现行制度更新。遇到多份同时标记为有效的版本，应暂停该文档的发布并交给管理流程处理，不能让模型猜哪份权威。

## 2. 为不同材料设计不同检查

Markdown 适合按标题、段落和代码块解析。PDF 要额外检查阅读顺序、页码与表格结构；扫描件还需要 OCR。表格中的「30」只有与列名「保留天数」和行名「生产数据库」一起保存，才有意义。

一种错误做法是把所有换行都删掉。原本的「仅适用于测试环境」可能因此被接到生产规则下面；列表里的例外条件也可能与主条款脱离。清洗的目标是减少排版噪声，同时保留语义边界。

入库抽检可以固定为四类样本：普通段落、表格、跨页内容、图片或扫描文字。对每类选几页，逐项比对原始材料与解析结果。发现解析质量不足时，将该文档标记为不可用于自动回答，而不是悄悄跳过错误。

微软的 RAG 文档把内容准备、检索、权限与更新列为需要共同处理的问题。这里采用的文档结构是本站设计，并不是 Azure API 的请求格式。[Azure RAG 概览](https://learn.microsoft.com/en-us/azure/search/retrieval-augmented-generation-overview)

## 3. 入库流程必须支持重跑

一个稳妥的流程是：发现变更 → 读取源文件 → 解析 → 质量检查 → 保存版本 → 生成分块 → 建索引 → 校验 → 激活。激活之前，新数据处于暂存状态，不影响线上查询。

重跑同一任务不应制造重复分块。可用「逻辑文档 ID、版本、解析器版本、分块规则版本」作为作业键；分块内容再保存自己的哈希。当分块规则升级时，即使原始正文不变，也能明确知道索引为什么需要重建。

```python
from hashlib import sha256

def content_hash(text: str) -> str:
    # 不随意删除空白；规范化规则应另外版本化。
    normalized = text.replace("\r\n", "\n")
    return sha256(normalized.encode("utf-8")).hexdigest()
```

这是完整可运行的小函数。它只做换行统一，不试图判断两个文档语义是否相同。不要把「哈希一致」解释为事实正确，哈希验证的是内容身份。

## 4. 删除与权限变更也是入库事件

只处理新增和修改会留下两个隐患：已经删除的内容仍被检索出来，已经撤销的权限仍通过缓存返回。需要把删除事件映射到逻辑文档 ID，撤下相关分块，并使相关回答缓存失效。

权限变化有时不改正文，因此只比较内容哈希无法发现。权限版本应单独记录，并在查询时检查。极简原型可以每次从当前元数据过滤；正式服务要验证索引同步延迟内的撤权行为，必要时增加实时权限校验。

## 5. 如何证明入库没有悄悄漏数据

为每次作业生成清单：源文档数、成功数、拒绝数、分块数与失败原因。若扫描到 100 份文件，只成功入库 92 份，系统应明确显示余下 8 份去了哪里。不要把「程序退出码为 0」当成内容完整性证明。

纸舟样例应至少覆盖：旧版本、当前版本、重复当前版本、空文档、权限撤销、源文件删除。正文与元数据分别变化时，都应触发正确处理。

## 本章练习与判断依据

手工建立 6 份教学文档，故意加入一份空文件、一份重复有效版本和一个表格。输出入库清单，解释每份材料是接纳、拒绝还是待修复。

验收重点是可追踪性：从任何一个检索片段都能找到原始文档、版本与解析规则；重复执行入库不会悄悄增加条目；被拒绝的材料有明确原因。
